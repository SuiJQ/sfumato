## 1. 产品定义

### 1.1 一句话

**把"局部蒙版"从用户的手动操作，变成管线的内部数据。**

传统软件要求你手动画天空蒙版，是因为它不知道哪里是天空。本工具不需要你画，因为分析阶段已经知道。

这不是"更聪明的滤镜"，而是**取消蒙版这道工序**。

### 1.2 与 Lightroom / 手机 AI 一键修图的区别

| | Lightroom | 手机 AI 一键 | 本工具 |
|---|---|---|---|
| 手动蒙版 | 必须 | 无 | 无（自动） |
| 手动调色 | 必须 | 无 | 可选 |
| 结果可复现 | 是 | 否（黑盒） | 是（参数化） |
| 批量一致 | 手动同步 | 否 | 是（同一套参数） |
| 出错可撤回 | 是 | 否 | 是（强度滑杆） |

### 1.3 三层控制

```
L0 万金油   永远开、不可关、目标"从不失败"
L1 可选项   开关，默认值由规则表决定（不是模型决定）
L2 手动     六根滑杆，全部是相对量，作用在 L0 之上
```

**所有手动值的语义是"相对万金油"，不是"绝对数值"。** 这条决定了三件事：

1. 一批图套同一套参数，色调天然一致
2. 滑杆拉回 0 → 精确等于万金油结果（不是原图）
3. 万金油可以单独迭代，不破坏用户存下的预设

### 1.4 非目标

不做生成式修改（不换天、不换脸、不去路人）。本工具只做**参数化调整**——这也是它可复现、可批量、可解释的根本原因。

## 2. 关键决策与被否决的方案

| # | 决策 | 备选方案 | 否决理由 |
|---|---|---|---|
| D1 | 纯前端，零后端 | Python 推理服务 | 自用工具；服务端渲染会让"预览=导出"变成两套实现，是最容易出不可对齐 bug 的架构 |
| D2 | 只写 WebGL2，不写 WebGPU | WebGPU 主 + WebGL2 回退 | 双份 shader 调试成本翻倍；桌面 WebGL2 覆盖率已足够 |
| D3 | 单 shader、单 draw call | 3 个 pass（降采样+主链+锐化） | 用 `generateMipmap` 的 mip level 4 直接当局部对比基准，省掉一整个 pass 和一张 render target |
| D4 | mask 打包进一张 RGBA8 | 三张独立 R8 纹理 | 一次采样代替三次；少两次绑定与生命周期管理 |
| D5 | 分区"增益"而非"三条曲线" | 三条曲线按 mask 混合 | 代码少一半，视觉 90% 等价；三条曲线易出色带 |
| D6 | shader 里没有 `amount` | shader 内做 `mix(identity, x, amount)` | **语义层（JS）负责 amount，shader 只吃数值**。identity 由构造保证，GLSL 无分支，测试可做到逐像素恒等 |
| D7 | 色彩运算分两段：线性光 + Oklab | 全程 sRGB / 全程 Lab | sRGB 里提饱和会偏紫偏黄；全程 Lab 会让局部对比出光晕。分工是：明度在线性光，色度在 Oklab |
| D8 | 导出只 JPEG | JPEG + PNG | 一种格式 = 一条编码路径 = 没有 alpha/位深/格式选择的所有边界情况 |
| D9 | 模型打进包，本地读盘 | 首次运行时下载 | 明确要求"打开不联网"；也避免 CDN 抖动与离线不可用 |
| D10 | 预设 = 小 JSON + 可选 LUT | 预设 = 完整参数快照 | 快照会随万金油升级而失真；小 JSON 只存"意图"（模块开关 + 六滑杆 + LUT id），跨图可复现 |

## 3. 运行形态与分发

`file://` 不能跑 Worker / WASM / fetch 本地文件（CORS）。三种形态：

| 形态 | 真·零网络 | 能否设 COOP/COEP | 评价 |
|---|---|---|---|
| **Tauri 打包** | ✅ | ✅ | 推荐。双击即开，能直写文件系统，能注入响应头 |
| 本地静态服务 `npx serve` | ⚠️ 走 localhost | 取决于服务 | 最轻，开发期用 |
| PWA + Service Worker | ✅（首次之后） | 需首访 https 或 localhost | 装一次，之后全离线 |

**COOP/COEP 的意义**：没有它就没有 `SharedArrayBuffer`，onnxruntime-web 只能单线程跑。
- 有：MASK 推理 ~150ms
- 没有：~300–600ms（仍在 Worker 内，UI 不卡）

结论：**P2 之前不依赖多线程**。单线程能接受，就不为它牺牲分发形态。

### 体积预算

| 项 | 大小 |
|---|---|
| 应用代码（JS + GLSL + HTML） | ~200 KB |
| onnxruntime-web wasm | 5–10 MB |
| modnet_int8.onnx | ~6.6 MB |
| face_landmarker.task | 3–4 MB |
| **合计** | **~20 MB，纯本地** |

自用工具，20 MB 无压力，换来的是**彻底不需要任何分发服务**。

## 4. 线程模型

```
Main Thread ── UI + WebGL2 预览（一次 draw）
  │
  │  拖动滑杆 → 只改 uniform → rAF 里画一帧
  │
  ├─ AnalyzeWorker（常驻，首帧之后 idle 时预加载模型）
  │    ImageBitmap(512px) → ORT 推理 → mask(RGBA8) + stats
  │
  └─ ExportWorker（导出时才起，用完即弃）
       全分辨率 ImageBitmap → 独立 OffscreenCanvas + WebGL2
       → 同一份 pipeline.glsl → readPixels → JPEG → File
```

**为什么 ExportWorker 要独立 GL 上下文**：`readPixels` 是同步阻塞调用。放在主线程会把 UI 冻住 100ms+；放在 Worker 里，阻塞的是 Worker，UI 照常 60fps。代价是多一份全分辨率纹理（24MP ≈ 96MB 显存），桌面可接受。

**预览与导出共用同一份 GLSL 源码**——这是整套架构最重要的性质。它消除了"预览好看、导出翻车"这一整类 bug。

**三个卡顿源与处置**：

| 来源 | 为什么会卡 | 处置 |
|---|---|---|
| 解码 24MP | 主线程 JPEG 解码 200ms+ | `createImageBitmap`（浏览器原生线程池），主线程不碰像素 |
| 模型推理 | WASM 在主线程直接冻住 | 常驻 Worker，384–512px 输入 |
| 导出编码 | `readPixels` + 编码是重的 | 独立 Worker + 独立 GL 上下文 |

补充三条：
- **滑杆事件合并**：`input` 只记最新值，rAF 里统一提交 uniform，拖再快也不排队
- **首帧策略**：先出 1024px 快速预览（不跑分析），分析回来再叠 mask。用户永远先看到东西
- **长任务让路**：mask 上采样、预设解析走 `scheduler.postTask({priority:'background'})`

## 5. 渲染管线

### 5.1 一次 draw call

```
上传纹理 → gl.generateMipmap()
        ↓
mip 0  = 原图（细节）
mip 4  ≈ 16×box 模糊（局部对比基准）
mask   = 一张 RGBA8（R=人像 G=皮肤 B=天空 A=255）
curve  = 一张 256×1 RGBA
        ↓
单个 fragment shader 完成全部运算
```

### 5.2 算子顺序

```
【线性光】
1. 白平衡 / 曝光
2. 高光柔化（rolloff，非硬截断）
3. 色调曲线（只作用在亮度，等比缩放 RGB → 保色相）
4. 阴影抬升

【Oklab】
5. 饱和度（全局 + 分区增益）
6. 肤色归一（不是"保护"）
7. 色相微调

【回线性光】
8. 局部对比（luma 加权，抑制光晕）
9. 锐化（限幅，杜绝白边）

【sRGB 编码后】
10. 3D 风格 LUT（P3 才有，tetrahedral 插值）
11. 颗粒 / 暗角 / 抖动
```

**为什么 LUT 放在编码之后**：`.cube` 文件按惯例是为 gamma 编码值设计的，放最后既符合行业约定，也省掉两次 pow。同时 LUT 天然是"最终外观"，不该被后续色调操作改写。

### 5.3 为什么这么排序

- **白平衡必须在最前**：在线性光里做增益，物理正确；在 sRGB 里做会让亮部偏色
- **曲线只作用亮度**：逐通道曲线会改变色相（暗部偏绿是经典症状）；按亮度缩放 RGB 保色相
- **色度在 Oklab**：感知均匀，提饱和不偏色
- **局部对比在锐化之前**：先定"该有多少层次"，再定"该有多锐"
- **颗粒在最后**：颗粒必须建立在实际输出的像素上，否则会被锐化当成细节放大

## 6. 数据流

```
用户拖入文件
   ↓
[校验] 扩展名 + MIME + 魔数 → 只收 JPEG/PNG
   ↓
[解码] createImageBitmap({imageOrientation:'from-image', premultiplyAlpha:'none'})
   ↓                                   ↘ 失败则提示（CMYK / 16bit / 超大图）
[首帧] 1024px 上传 → 万金油默认参数 → 立刻可交互
   ↓
[分析] 512px → AnalyzeWorker → mask + stats（~150–600ms，异步）
   ↓
[叠加] mask 就绪 → 重新上传纹理 → 分区增益生效
   ↓
[交互] 六根滑杆 / 模块开关 → JS 映射层 → uniform → rAF
   ↓
[守门] 分析结果中已有统计量，估算处理前后质量差 → 必要时回退强度
   ↓
[导出] 原图 bitmap transfer 给 ExportWorker → 同 shader 全尺寸重放
       → 白底铺平 → JPEG q0.93 → File → 保存
```

## 7. 万金油的定义（重要）

万金油不是"一组好看的参数"，是**一组有上下文的策略**：

| 步骤 | 依据 | 为什么必须自适应 |
|---|---|---|
| 白平衡 | 灰世界 + 皮肤/人脸加权 | 纯灰世界会把夕阳调成灰 |
| 曝光 | 亮度中位数对齐到 0.5 | 固定 EV 会让暗图更暗 |
| 曲线锚点 | 直方图 p1 / p50 / p99 | 固定 S 曲线在低对比图上会过冲 |
| 高光柔化 | 白点位置 | 逆光图需要更强 rolloff |
| 局部对比 | 噪点估计 | 噪点重的图加对比 = 加噪 |
| 强度 s | 噪点 + 动态范围 | 低质量图自动降到 0.7 |

**核心原则：万金油的 KPI 是"没人关掉它"，不是"一眼惊艳"。** 惊艳交给风格层。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| mask 边缘光晕（头发、栏杆、树叶） | 直接毁掉"不用抠图"的卖点 | shader 内做联合双边上采样（用原图亮度做引导）；接受"不完美"，但绝不出现硬边 |
| Chrome/Safari 色彩管理行为不一致 | 预览与导出颜色不同 | 全程显式声明 sRGB；导出不带 ICC（业界默认按 sRGB 解）；P3 列为已知限制并写进 UI |
| `file://` 无法运行 | 用户双击打不开 | 明确分发形态；提供 Tauri 包 |
| onnxruntime 默认从 CDN 拉 wasm | 违背"不联网" | 强制 `ort.env.wasm.wasmPaths = './ort/'`，并在离线环境跑一次冒烟测试 |
| 显存泄漏 | 连续修图后标签页崩溃 | 每次换图强制 `deleteTexture` + `bitmap.close()`；上限 1 张活动图 |
| 大图（>50MP） | 显存爆 | 直接拒绝并提示，不做降级 |
| 万金油过猛 | 用户第一件事就是关掉它 | 所有参数取保守值 + 守门员回退；上线前跑 50 张不同题材的"不劣化"测试 |

## 10. 整体验收（项目级）

1. **不劣化**：50 张跨题材照片，万金油处理后无一张主观变差（守门员记录）
2. **一致性**：同一预设套 10 张同场景照片，色调差异 ΔE00 中位数 < 3
3. **可用性**：从拖入到导出，除拖拽外零操作可完成
4. **可解释**：任何效果都能拆回到某根滑杆 / 某个开关
5. **可离线**：拔网线，全功能可用
6. **代码量**：实测 29 个文件 / 4033 行（TS + GLSL + CSS，不含模型与第三方库）。
   超出原定 1500 行的预算，超支主要在 `analyze.worker`（模型接入 + 启发式 mask）、
   `lut/*`（解析/重采样/迁移烘焙）、`storage` 与 UI 层。取舍是：这些模块彼此独立、
   可单独测试，比压行数更值得。
